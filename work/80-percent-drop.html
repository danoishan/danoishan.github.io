Case 01 · customer data / CRM

The 80% Drop

Reported form submissions collapsed after a CRM migration. The useful question was not “which form is broken?” It was “where did the end-to-end customer path stop being observable?”

The problem looked smaller than it was.

A company completed a significant CRM migration. Soon after, the marketing team saw an abrupt decline in reported inbound form submissions. Historical behaviour suggested a steady flow of leads. The new reporting suggested that demand had nearly disappeared.

Website traffic did not show a comparable collapse. That mismatch mattered. It meant the safest first assumption was not “customers stopped converting.” It was “the measurement or submission chain changed.”

I did not start by rebuilding forms. I started by asking what had to be true for a visitor to become a measurable marketing record.
Artifact 01End-to-end path
Visitor→Website form→Submission capture→CRM record
CRM record→Identity→Consent→Campaign attribution→Reporting

My first move: split one symptom into four layers.

The original symptom was “form volume is down.” That was too broad to troubleshoot and too narrow to describe the system. I split the investigation into four layers so every finding had a place and an owner.

1. Capture

Can a visitor submit? Does the page preserve the form long enough for the handler to capture it? Do all forms follow the same implementation pattern? Can we reproduce success and failure?

2. Consent

Are the required tracking and consent services actually enabled? Are marketing events being captured under the expected consent state? Is the implementation consistent with how the organization wants to use behavioural data?

3. Identity

Once data is captured, can it resolve to the intended customer or contact? Are the right source objects and relationships available? Is identity resolution configured far enough to support the planned segmentation and reporting?

4. Attribution

Even if the lead exists, can marketing connect it to the form, campaign, landing page or flow that generated it? If not, the lead may be operationally present while still being invisible in marketing performance reporting.

What the audit surfaced.

The important finding was that there was no single failure. The migration had exposed gaps across multiple parts of the marketing stack. Fixing only the visible form issue would have produced a partial recovery and left the customer with the same underlying observability problem.

The audit also changed the stakeholder conversation. Instead of debating whether one dashboard was accurate, we could point to concrete breakpoints in the customer-data chain and decide which capability had to be trustworthy first.

The decision was sequencing, not a giant rebuild.

The tempting response to a messy platform state is to bundle everything into one modernization project. I recommended the opposite: restore confidence in the chain in dependency order, so each phase created evidence for the next.

PHASE 1

Reliable capture

Confirm the production form path, baseline expected volumes, reproduce failures and establish an end-to-end submission test.

PHASE 2

Customer-data visibility

Enable the required consent / tracking foundation, confirm source data and relationships, and validate identity behaviour.

PHASE 3

Attribution + reporting

Connect forms and flows to campaign structures, then validate that marketing reporting reflects the same records seen operationally.

Why this order?

Attribution is useless if capture is unreliable. Segmentation is risky if identity is unresolved. A polished dashboard is dangerous if the underlying event chain is not trustworthy. The roadmap therefore followed technical dependencies rather than stakeholder preference for the most visible output.

What I owned, and what I deliberately did not.

I owned

  • Discovery questions and audit structure
  • Problem decomposition and prioritization
  • Cross-functional working sessions
  • Dependency and decision tracking
  • Recommended implementation sequence
  • Level-of-effort / scope coordination
  • Client communication and next-step clarity
  • End-to-end validation approach

Specialists owned

  • Production code changes
  • Platform-specific configuration implementation
  • Source-system changes
  • Final architecture approval where specialist authority was required
  • Marketing campaign strategy and creative

That boundary is important to me. Technical delivery leadership does not mean pretending to be the engineer writing every production change. It means creating enough technical clarity that the right owner can act, and making sure the combined system reaches a safe outcome.

The launch artifact was a proof plan.

The recovery was not “done” when configuration was changed. It was done when the same customer action could be traced from the website through the operational record and into the intended marketing view.

Known test submission accepted in browser
Expected record created / updated
Consent state matches test scenario
Identity resolves to intended profile
Campaign / source attribution persists
Reporting reflects the same test record
Negative / opt-out case behaves correctly
Owner and rollback path documented

The broader outcome was a move from “our numbers look wrong” to a prioritized technical roadmap with explicit dependencies, ownership and validation criteria. That is the kind of shift I try to create in ambiguous programs.

What I would do differently next time.

I would define the observability baseline before the migration begins: expected form volumes, canonical test records, source-to-report lineage and named owners for every system boundary. Migrations often focus heavily on moving data and configuration. The ability to prove that the new system is behaving like the old one deserves the same planning discipline.

The lesson was not “forms are fragile.” It was that customer journeys become hard to debug when the organization cannot see across system boundaries.
