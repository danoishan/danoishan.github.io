The 80% Drop

A CRM migration appeared to wipe out most inbound demand. Instead of assuming customers had stopped converting, I led the investigation across the website, unstable form behaviour, Salesforce capture, consent, identity and attribution to find where the customer path had stopped being observable.

The metric said demand collapsed. The traffic did not.

After a significant CRM migration, reported inbound form submissions dropped sharply. Historically, the business saw a steady stream of leads. The new reporting suggested that demand had nearly disappeared.

But website traffic did not show a comparable collapse. That mismatch changed the starting assumption. The safest question was not “why did customers stop converting?” It was “where did the end-to-end customer path stop being observable?”

I did not start by rebuilding forms. I started by mapping every handoff required for a visitor to become a measurable marketing record.
Artifact 01End-to-end path
Visitor→Page interaction→Form→Submission capture
CRM record→Consent→Identity→Attribution→Reporting

I split one symptom into four layers.

1. Capture

Can the user actually see and submit the form? Does dynamically loading it change the behaviour? Does the browser show a request, error or blocked response? Do different form patterns behave differently?

2. Consent

Are tracking and consent capabilities enabled and aligned to the intended marketing use cases? Is behavioural visibility available under the expected consent states?

3. Identity

Once captured, can the record resolve to the intended person or account? Are the required source objects, fields and relationships actually available for the desired segmentation and reporting?

4. Attribution

Even if a lead exists, can marketing connect it back to the form, landing page, campaign or flow that generated it?

Then we found a concrete breakpoint at the system boundary.

Some forms worked when rendered as simple standalone embeds, but became slow or unpredictable when loaded dynamically inside the website experience. The implementation crossed browser JavaScript, iframe behaviour, CORS and Salesforce form technology, with different teams owning different parts of the chain.

That made the troubleshooting approach more important than the product label. We reproduced the failure, separated page behaviour from platform behaviour and translated the evidence into specific actions for the web and Salesforce teams.

For the unstable embedded experiences, the team moved toward a visitor-facing external form connected through Salesforce Form Handler, with explicit field names, conditional logic, hidden values, staging and end-to-end testing defined before production.

The visible form problem was real, but it was not the whole problem.

The broader audit surfaced gaps across capture, consent, identity, attribution and operations. Fixing only the JavaScript / embedded form issue would have improved one breakpoint while leaving the organization unable to fully trust the customer data chain.

The answer was sequencing, not one giant rebuild.

I recommended restoring trust in dependency order so each phase created evidence for the next.

PHASE 1

Reliable capture

Stabilize the form path, replace problematic embedded patterns where needed, baseline expected volumes and prove submission end to end.

PHASE 2

Customer data visibility

Enable the consent / tracking foundation, confirm source data and relationships and validate identity behaviour.

PHASE 3

Attribution + reporting

Connect forms and flows to campaign structures and validate that marketing reporting reconciles with operational records.

Attribution is useless if capture is unreliable. Segmentation is risky if identity is unresolved. A polished dashboard is dangerous if the underlying event chain is not trustworthy.

The work moved through specialists. My job was to keep the handoffs intact.

I did not need to own every line of production code to own delivery. I needed to make sure the context, evidence, decision and acceptance criteria survived each handoff.

Artifact 04Team + handoffs
Client / strategy→Delivery lead→Web engineering→Salesforce specialists
Salesforce specialists→QA / UAT→Client owners→Rollout / monitoring

I owned / handed off

  • Business impact, reproduction evidence and problem framing
  • Clear requirements and questions for web engineering
  • Field, form and process requirements for Salesforce specialists
  • Dependencies, owners, scope and decision tracking
  • Acceptance criteria and end-to-end test scenarios for QA / UAT
  • Client communication, rollout sequencing and next step decisions

Specialists owned

  • Production JavaScript / web changes
  • Salesforce configuration implementation
  • Form Handler setup details
  • Source system changes
  • Technical test execution and defect fixes
  • Final architecture approval where specialist authority was required

A technical fix was not enough. The client team needed a pattern they could trust and reuse.

The rollout approach went beyond “put the fix in production.” I stayed involved through staging, stakeholder walkthroughs, release documentation, monitoring ownership and the decision about where the stabilized pattern should be reused next.

01

Introduce safely

Prove the new pattern in staging and on a controlled set of forms before treating it as the new standard.

02

Enable the users

Give client and operational teams clear documentation, expected behaviour, ownership and escalation paths so the change can be operated without relying on project memory.

03

Watch adoption

Compare submission volumes, support issues and stakeholder feedback against the baseline to distinguish adoption problems from technical failures.

04

Scale the pattern

Once the path is stable and observable, use the same implementation and validation model for additional forms, campaigns and customer data use cases.

The final artifact was not a status report. It was a proof plan.

Known test submission accepted in browser
Expected record created / updated
Conditional logic and hidden values persist
Consent state matches test scenario
Identity resolves to intended profile
Campaign / source attribution persists
Reporting reflects the same test record
Negative / opt-out case behaves correctly

The conversation moved from “our numbers look wrong” to a prioritized technical roadmap with concrete breakpoints, owners, dependencies, handoffs, acceptance evidence and a path to broader rollout.

What I would do differently before the next migration.

I would define the observability baseline before migration begins: expected form volumes, canonical test records, known page behaviours, source-to-report lineage, named owners for every system boundary and an explicit enablement / adoption plan for the teams who will operate the new process.

The lesson was not “forms are fragile.” It was that customer journeys become hard to debug and hard to adopt when the organization cannot see or own the handoffs.
