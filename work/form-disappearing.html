Case 03 · integration troubleshooting

The Form Was Disappearing

A web form, page JavaScript, CORS configuration and a Salesforce form handler sat across different ownership boundaries. The fastest path to a fix was to stop treating “the form” as one component.

ANONYMIZED · Based on a real troubleshooting sequence. Client name, URLs and non-essential implementation details are removed.

SymptomSubmission path fails in production testing
SystemsBrowser · JavaScript · CORS · Salesforce
My roleEvidence + coordination + retest
Key lessonDebug the boundary, not the label

A small bug with four possible owners.

A client team was implementing a web form that needed to submit into a Salesforce-backed process. From the user's perspective the interface looked normal. During technical testing, however, submissions were not consistently reaching the expected handler.

That kind of issue is easy to bounce between teams: web says Salesforce is rejecting it; platform says the request never arrived correctly; the client sees a form on screen and assumes the integration is the only variable.

The first job was to turn “it doesn't work” into evidence that could survive a handoff between teams.

I used the request path as the troubleshooting tree.

Instead of asking each team to inspect its own component in isolation, I organized testing around the order in which a request had to succeed.

Artifact 01Diagnostic tree
1. User submits→2. Form remains available→3. Browser sends request
3. Browser→4. Origin allowed?→5. Handler receives→6. Salesforce process runs

Each step generated a yes/no question. Could the browser make the request? Was the origin accepted? Did the form still exist at the moment the handler attempted to capture it? Did Salesforce receive the request? Did the automation execute after receipt?

Two separate failures appeared.

Finding 1: page JavaScript changed the form before capture

Testing showed that page-level JavaScript was removing or replacing the form during the submission sequence. That meant the handler could not reliably capture the expected form state. The CRM integration was not the only variable; the page itself was altering the object the integration depended on.

Finding 2: the test origin was not being recognized

A separate validation produced a CORS error from the test domain. The allowed-origin configuration appeared to be the relevant control, so the next action was to confirm the exact origin entry and, if the configuration was already present but not effective, escalate through platform support rather than repeatedly changing application code.

Artifact 02Evidence matrix
ObservationWhat it ruled outNext owner
Form removed before handler captureNot solely a Salesforce handler defectWebsite / front-end team
Browser reports CORS failure from test originNot an audience or downstream automation issuePlatform configuration owner
Exact origin confirmed in configurationReduces likelihood of simple entry typoPlatform support if behaviour persists

My role was not to claim somebody else's code.

Technical customer-facing work gets weaker when the project lead blurs ownership. I wanted the evidence and test path to be mine; implementation stayed with the specialists who owned the system.

I owned

  • Reproduction steps
  • Cross-system hypothesis tree
  • Evidence shared with each owner
  • Clarification of exact configuration required
  • Sequencing of fixes and retests
  • Client communication
  • End-to-end closure

System owners owned

  • Page JavaScript changes
  • Production website code
  • Salesforce configuration changes
  • Backend platform action / support escalation
Engineering owned the production changes. I owned the investigation structure, the evidence, the test plan and making sure the customer got to a safe outcome.

The fix was not complete until the boundary was retested.

After changes, the test had to repeat the same request path and confirm both success and expected negative behaviour.

Form remains present through submission
Request leaves browser without CORS rejection
Expected handler receives payload
Salesforce record / process executes
Success state visible to user
Known invalid submission fails safely

This is a small case, but it is representative of the work I like: enough technical depth to make the problem precise, and enough delivery ownership to make sure precision turns into action.

The reusable lesson was about interfaces.

The phrase “Salesforce form issue” would have sent the whole team toward one product. The actual failure crossed browser behaviour, front-end code, network security and platform configuration. The label was less useful than the request path.

When several systems are involved, I now default to drawing the boundary first: what leaves system A, what system B expects, what evidence exists in between, and who can change each layer.
