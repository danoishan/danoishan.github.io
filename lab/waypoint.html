Waypoint: design the lifecycle stack

A fictional travel company wants abandoned-search reminders, price-drop alerts, booking messages and destination recommendations across mobile and web. The hard part is not drawing a Canvas. It is deciding what each system should own.

CompanyFictional travel marketplace
Scale2M registered · 650k MAU
StackMobile/Web · Braze · Snowflake · APIs
GoalReliable lifecycle activation

The brief.

Waypoint is a mobile-first travel marketplace. Users can browse anonymously, create an account, save destinations, search flights, book trips and receive email, push and in-app messages.

The lifecycle team asks for five use cases:

  • Abandoned-search reminders
  • Price-drop alerts on saved destinations
  • Booking confirmation and pre-trip messaging
  • Post-trip review requests
  • Personalized destination recommendations

Waypoint already has a Snowflake warehouse and backend booking service. Braze will power orchestration and customer messaging.

The architecture question is not “How do we send these messages?” It is “Which system is authoritative for each fact, and how should that fact reach the messaging layer?”

Four design principles.

01

Source truth where it originates.

Bookings belong to the booking service. Device behaviour belongs to the client. Durable customer attributes belong in the warehouse or source system that governs them.

02

Use events for moments, attributes for state.

“Searched Paris at 14:32” is an event. “Preferred airport = YYZ” is durable profile state. Mixing them creates awkward segmentation and data churn.

03

Identity changes once, intentionally.

Anonymous behaviour can exist before login. The transition to a known user must be explicit and consistent so profiles do not fragment.

04

Design the exit before the message.

An abandoned-search journey is only safe if a later booking can suppress or exit the user before an irrelevant reminder is sent.

Identity: anonymous first, known later.

Waypoint should allow anonymous users to generate useful behavioural events without inventing permanent customer identifiers too early. When the user authenticates, the app explicitly changes to the canonical customer ID used across backend systems.

Artifact 01Identity flow
Anonymous app user→ SDK →Anonymous Braze profile
Login / sign-up→ change_user(customer_id) →Identified profile
Backend services→ same customer_id →Identified profile

Why not assign a random external ID on first app open?

Because it creates an identity contract the business then has to maintain forever. If Waypoint already has a canonical customer identifier after authentication, anonymous SDK identity can remain anonymous until there is a real customer to attach it to.

SDK vs REST: decide by ownership and reliability.

Client behaviour that naturally occurs in the app should be captured by the SDK. Server-authoritative facts such as bookings, refunds and subscription changes should be emitted by backend services. The question is not “which endpoint is easier?” It is “which system is allowed to say this happened?”

Example backend event

POST /users/track
{
  "events": [{
    "external_id": "cust_18427",
    "name": "booking_completed",
    "time": "2026-08-31T14:32:00Z",
    "properties": {
      "booking_id": "BKG_92118",
      "destination": "Paris",
      "departure_airport": "YYZ",
      "departure_date": "2026-09-18"
    }
  }]
}

The payload intentionally carries enough context for orchestration and personalization, but not every booking field. Braze should not become a second booking database.

The warehouse is for durable profile state and derived context.

Snowflake already contains booking history, loyalty state, market preference and customer value. Rather than replay historical behaviour as artificial events, Waypoint syncs the profile attributes needed for segmentation and personalization.

Artifact 02Data responsibility
Booking service→ events →Braze
Mobile / web→ behaviour →Braze
Snowflake→ durable attributes →Braze
Braze→ orchestration →Email / Push / IAM

Warehouse attributes

  • loyalty_tier
  • preferred_airport
  • home_market
  • lifetime_bookings
  • last_trip_date
  • predicted_destination_cluster

These are useful because they describe durable or derived customer state. They can update on a scheduled cadence without pretending to be real-time events.

Abandoned search: design the exit first.

A user searches Toronto → Paris but does not book. Waypoint wants a reminder after two hours. The obvious build is a delay then a message. The safer build asks whether the business outcome already occurred.

Artifact 03Journey logic
search_completed→2 hour delay→Booked same itinerary?
YES→Exit
NO→Eligible + consented?→Reminder

Additional guardrails

  • Cap reminders to avoid one message per search
  • Exit when booking_completed arrives
  • Suppress customers who opted out of the relevant channel
  • Do not message when the departure date is too close for the reminder to be useful
  • Prefer the most recent qualifying search if multiple searches occur
  • Measure booking conversion after message and against a control group

Test the customer path, not just the message.

I would create named synthetic users covering identity, consent and event-order scenarios. The objective is to prove the architecture across systems.

Anonymous search creates expected event
Login merges future activity to canonical ID
Backend booking event reaches same profile
Booking exits abandonment journey
Opted-out user never receives email
Stale / missing attribute uses safe fallback
Duplicate event does not duplicate outcome
Control cohort remains unmessaged

Observability

For launch week I would reconcile source event counts, Braze ingestion counts, journey entries, exits, sends and conversion. If those numbers disagree, the team should know exactly which owner investigates each gap.

Roll out in layers.

01 / INSTRUMENT

Events + identity

Implement SDK and backend event contracts. No customer messaging yet. Validate schemas and profile behaviour.

02 / SHADOW

Journey without send

Run entry/exit logic against test and internal cohorts. Reconcile expected vs actual eligibility.

03 / PILOT

Small audience

Release one use case to a limited market with control group and monitoring.

Only after event quality, identity and exits are stable would I scale to price-drop and recommendation use cases. The goal is to avoid debugging five business journeys while the underlying identity model is still moving.

What changes at 10M users?

The conceptual architecture can stay similar, but operating discipline becomes more important:

  • Formal event-schema ownership and versioning
  • Automated contract tests between source services and messaging ingestion
  • Capacity / rate-limit modeling for backend event bursts
  • More explicit data-retention and privacy governance
  • Regional / market-specific consent rules
  • Stronger observability and alerting around ingestion lag
  • Reusable lifecycle components instead of one-off Canvases
  • Change-management standards for events consumed by multiple downstream journeys
At scale, the most valuable artifact is not the journey diagram. It is the contract between systems and teams that lets the journey remain trustworthy as everything around it changes.
