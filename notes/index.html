Notes / working principles / references

Things I keep coming back to.

Not a content strategy. Just a notebook for ideas that make technical delivery clearer, plus a few books and references worth keeping nearby.

01 Operating notes02 Technical notes03 Noteworthy

Operating notes.

A schedule is not a dependency map.

Dates answer “when.” Dependencies answer “what has to be true first.” In complex programs, the second question is usually more important. A date attached to unresolved identity, access, source data or ownership is not a plan; it is a guess with formatting.

Go/no-go should be boring.

The final launch conversation should confirm evidence, not discover whether the team is ready. If QA status, rollback, consent, audience counts or monitoring ownership are first discussed at go/no-go, the delivery controls failed earlier.

Write down the decision, not just the meeting.

Meeting notes decay quickly. I care about the durable part: what was decided, what alternatives were rejected, why the choice was made, who owns it, and what new evidence would justify reopening it.

RAID is useful only when it changes behaviour.

A risk register is not useful because it contains risks. It is useful when a named risk changes sequencing, scope, ownership, monitoring or a stakeholder decision. Otherwise it is administration.

Technical notes.

SDK vs REST is usually an ownership question.

Client behaviour should usually originate where the behaviour happens. Server-authoritative outcomes should usually originate where the business transaction becomes true. The transport decision follows the source-of-truth decision.

Events describe moments. Attributes describe state.

“Customer booked Paris” and “customer has three lifetime bookings” can both be useful in lifecycle marketing, but they are different shapes of information. Treating durable state as a stream of pseudo-events makes downstream logic harder than it needs to be.

The system boundary is where I start debugging.

If browser, web app, API, CRM and marketing platform are involved, I want to know exactly what leaves each system, what the next system expects and what evidence exists at the handoff. Product labels are less useful than request paths.

Design the exit before the message.

For any triggered journey, ask what business event should make the message irrelevant. Booking, purchase, cancellation, service completion or a consent change often matters more than the original trigger.

Noteworthy.

A small list of material I think is worth revisiting. The comments are the point; the list is not meant to be exhaustive.

BOOK / SYSTEMS

Thinking in Systems — Donella Meadows

A useful reminder that fixing the visible output is not the same as changing the system that produces it.

BOOK / OPERATIONS

The Goal — Eliyahu Goldratt

Good for thinking about constraints, flow and why optimizing every local team can still make the whole system worse.

BOOK / EXECUTION

The Checklist Manifesto — Atul Gawande

I like the central idea: expertise does not remove the need for simple controls when complexity exceeds human memory.

BOOK / MANAGEMENT

High Output Management — Andrew Grove

Still useful for leverage, operating cadence and thinking about management as a system rather than a personality.

PRACTICE

API documentation before implementation

Reading the limits, identity model, error behaviour and data contract early is usually faster than learning them through a failed integration later.

PRACTICE

Synthetic test users

A small set of named, reusable test profiles across consent and lifecycle states makes end-to-end validation dramatically easier.
