SEP 2026 · Practice note · QA / lifecycle

Synthetic test users make end-to-end QA dramatically easier.

A reusable set of named test profiles across identity, consent and lifecycle states creates a shared language for proving that customer journeys actually behave as intended.

01 Problem02 Test set03 Rules04 Value

Ad hoc test data makes QA harder than it needs to be.

When every release creates new test users on the fly, teams spend time reconstructing states instead of testing behaviour. One person tests an opted-in customer, another uses a profile with incomplete identity, and a third unknowingly reuses a record whose history already changed the result.

A reusable test profile is not fake data. It is a controlled instrument for proving system behaviour.

I prefer a small, named test set.

The exact profiles depend on the program, but the structure usually covers the important branches:

ExampleReusable lifecycle test set
ProfileStateWhat it proves
TEST-01Known + fully consentedHappy path / intended entry and message
TEST-02Known + opted outSuppression / consent enforcement
TEST-03Anonymous → identifiedIdentity transition and profile continuity
TEST-04Eligible at trigger, then convertsExit logic before message
TEST-05Missing required source attributeFailure handling / exclusion
TEST-06Duplicate or replayed eventIdempotency / duplicate protection

The profiles need operating rules.

  • Give each profile a stable purpose and owner.
  • Document the expected state before each scenario.
  • Reset only what must be reset, and record when the state changes.
  • Keep identifiers obvious enough that nobody mistakes them for real customers.
  • Use the same profiles across source systems when end-to-end lineage matters.
  • Pair each profile with an expected outcome so screenshots and logs have context.

The value is shared evidence.

Synthetic users make debugging faster because everyone is talking about the same record. Marketing can point to the expected message, engineering can inspect the event and payload, data teams can trace the source record, and QA can compare actual behaviour with a pre-agreed scenario.

They are especially useful for negative tests. It is easy to prove that a message sent. It is more important to prove that the customer who should not receive it did not.
