SEP 2026 · Technical note

Events describe moments. Attributes describe state.

Lifecycle logic gets easier when transient behaviour and durable customer state are modeled differently.

Both can describe the same customer, but they answer different questions.

“Customer booked Paris” is a moment. “Customer has three lifetime bookings” is state. One is useful for triggering a journey around what just happened. The other is useful for segmentation and decisions that need the current truth.

Use events to remember that something happened. Use attributes to know what is true now.

Why the distinction matters.

If durable state is represented only as a stream of events, every downstream team has to reconstruct the current answer. If every moment is flattened into attributes, you lose useful sequence and timing.

ExamplesModel choice
DataShapeUseful for
Search abandonedEventTriggering a timely follow-up
Purchase completedEventConfirmation / post-purchase orchestration
Loyalty tierAttributeCurrent segmentation
Lifetime booking countAttributeEligibility / personalization
Last purchase dateAttribute derived from eventsLapse logic / reporting

Some data should exist in both forms.

A purchase can be an event because the moment matters, while lifetime purchase count and last-purchase date are durable state updated as a consequence. The mistake is assuming the same shape should serve every use case.

The practical rule.

Ask whether downstream users need to know that something happened, what is true now, or both. Model from that requirement rather than from whichever API field is easiest to populate.
