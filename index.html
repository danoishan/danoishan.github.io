03 / How I think

Four rules I use when the work gets messy.

These principles guide the decisions underneath the project mechanics.

01

Find the system boundary.

Most messy technical problems get easier once you identify where ownership changes from one system or team to another. That is often where the missing requirement, assumption or failure lives.

02

Separate “can” from “should.”

A platform being technically capable of something does not make it the right architecture. I want the business case, data readiness, operating cost and customer impact in the same decision.

03

Sequence dependencies before dates.

A beautiful schedule is fiction if identity, source data, environment access or decision ownership is unresolved. Dependencies create the schedule, not the other way around.

04

Define proof before launch.

If nobody has agreed what evidence constitutes a successful end-to-end test, the project is not ready. I want acceptance criteria and observable proof before the go/no-go conversation.

04 / Notes

Things I keep coming back to.

Short operating notes, technical concepts and references I find useful.

OPERATING NOTE

A schedule is not a dependency map.

Dates tell you when. Dependencies tell you whether the date is even possible.

TECHNICAL NOTE

SDK vs REST is usually an ownership question.

Where the event originates, who owns the source of truth and what must happen if a client is offline matter more than “which API is easier.”

LAUNCH NOTE

Go/no-go should be boring.

If the final launch meeting is where teams discover whether data, QA or rollback is ready, the control system failed earlier.

WORKING STYLE

Write down the decision, not just the meeting.

Teams remember conversations differently. A useful decision log captures the choice, why, owner, assumptions and what would cause a revisit.
